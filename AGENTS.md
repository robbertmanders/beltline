# Repository Guide

Beltline runs work through belts: a trigger (GitHub issues with a label, pull requests that ask for your review, except those from forks, Jira tickets from a JQL query, a schedule, or tasks you start) plus stages (agents, approvals, watches), each ending in a named outcome that decides what happens next. It is two parts on one Mac: `beltlined`, a headless Go daemon (`daemon/`) that owns the data folder, every decision and every derived view, and serves a local versioned API; and a TypeScript and React web app (`Web/`) that only shows what the API returns and sends your commands.

The one rule for where code goes: **the daemon owns every fact and every decision; the web app owns only pixels, navigation and unsent input.** If two browsers looking at the same data could disagree about something, it belongs in the daemon. The daemon reads and writes the data folder, runs the loop and every side effect (`gh`, `acli`, `git`, `tmux`, the agent CLIs), decides which actions a run, belt or agent allows (each resource carries `actions`, with the reason one is unavailable), validates every save, and computes every derived view: statuses, cost, Work grouping and filters, run links, placeholder help, the parsed Markdown blocks, and the structure of each belt drawing (its stages, merged machines, fork routes, which track is travelled), and the geometry of the Floor and of a run's metro map. The web app lays out the rest in pixels (rows and grids in CSS, tracks in SVG), keeps routes and selection, form state until you send it, and display preferences (folds, widths, sidebars) in `localStorage`. It never reads files, calls GitHub, Jira, git or tmux, decides whether an action is allowed, validates beyond "this field is empty", computes a status, cost, grouping or which stage connects to which, or keeps anything a daemon restart needs. The daemon keeps no per-browser display state.

## Working rules

- `make quick` is `go vet` and every Go test except the tmux, PTY and stand-in agent ones, then the web typecheck and tests (about a minute); `make test` runs the same with the integration tests. `make test` adds those integration tests (`-tags integration`, with the stand-in agent in `daemon/testdata/fixtures/`) , and `make check` builds, runs `make test` and the script checks (about five minutes). `make race` runs the Go tests under the race detector, about ten times slower, and is not part of `make check`. `cd daemon && go test ./internal/<package> -run <Name>` runs one test. Every test with its own temp folder and fakes calls `t.Parallel()`; the tmux tests each start a private server, `beltline-test-<pid>-<n>`, and remove it. `cd Web && npm run typecheck` runs the typecheck alone (it first writes the gitignored `src/api/golden.gen.ts`, see the contract tests below), and `cd Web && npm test` the web tests alone.
- `make lint` checks the daemon with golangci-lint `v2.14.0`, the one version it accepts, under the checked-in `.golangci.yml` (`govet`, `staticcheck`, `errcheck`, `ineffassign`, `unused`). It runs over `./...` with its tests twice, without and with `-tags integration`, and runs `gofmt -s -l` over every tracked Go file under `daemon/`, so files a build tag leaves out are checked too. It reports findings and tool errors with a failing status and never rewrites a file; format with `gofmt -s -w <files>` instead. It does not run tests or install anything. Install the pinned release once, into `~/go/bin` (on `PATH` for most Go setups; otherwise pass `GOLANGCI_LINT=/path/to/golangci-lint` to make). The commands are for Apple silicon; use `darwin-amd64` on Intel Macs:
  ```sh
  version=2.14.0; arch=arm64; archive="golangci-lint-$version-darwin-$arch.tar.gz"
  base="https://github.com/golangci/golangci-lint/releases/download/v$version"
  work=$(mktemp -d) && cd "$work" && curl -fsSLO "$base/$archive" && curl -fsSLO "$base/golangci-lint-$version-checksums.txt"
  grep " $archive\$" "golangci-lint-$version-checksums.txt" | shasum -a 256 -c - && tar -xzf "$archive"
  mkdir -p ~/go/bin && cp "golangci-lint-$version-darwin-$arch/golangci-lint" ~/go/bin/ && golangci-lint version --short
  ```
  The last line must print `2.14.0`. Run `make lint` before you commit a Go or `.golangci.yml` change, after `make quick`; `quick`, `test` and `check` keep their meanings and do not run it. Suppressions follow one standard: fix the finding first. When a fix would be wrong, put `//nolint:<linter> // <reason>` on the flagged line, naming that one check and why it is safe there. Never disable a linter, a whole package or the test files, add a path exclusion, or skip a requested check to get a pass; a new `_ =` discard of an error gets a comment saying why the error can be dropped.
- Which checks to run. Several agents often work on this Mac at once, so test what the change touches, not everything, and never the full suite twice for one change:
  - A fresh checkout or worktree has no `Web/node_modules`: run `cd Web && npm ci` once before any web test, typecheck or `make` target that uses the web app.
  - While you iterate, run the tests of the packages and files you changed: `cd daemon && go test ./internal/<package>` (with `-run <Name>` for one test), `cd Web && npx vitest run <file>`, and `npm run typecheck` after TypeScript changes. A wire change also needs `go test ./internal/server/...`, which checks `Web/src/api/wire.gen.ts` against the Go wire types and fails when the file is out of date (see the `TestTypeScript` note below); `BELTLINE_UPDATE_GOLDENS=1 go test ./internal/server/api -run TestTypeScript` rewrites it. Then run `npm run typecheck`.
  - Before you commit, run `make quick` once, and `make lint` too when the change touches Go or `.golangci.yml`. Run `make test` or `make check` instead only when the change touches the tmux, PTY or runner code, the stand-in agent, `scripts/` or the build; `make race` and `make snapshots` only when the task asks for them or for captures, and then narrowed with `BELTLINE_SNAPSHOT_ONLY` and `BELTLINE_SNAPSHOT_SIZE`.
  - `make quick`, `make test` and `make check` take a machine-wide lock (`/tmp/beltline-suite.lock`), so suites started at the same time run one after another; a wait there is another agent's suite, not a hang, so don't kill it or work around the lock.
  - A test that fails in a full run and passes when run alone is load, not your change: run that test again alone, note it, and move on rather than repeating the suite, lowering its parallelism or raising its timeouts.
  - Write the commands you ran and their results down where your task asks for them. A stage that reviews or verifies someone else's change does not run the suites, linters or typecheck again: it reads the change, its tests and the builder's recorded results, and runs a single named test only when reading can't settle whether a behaviour holds.
- Packages under `daemon/internal/`, each importing only the ones before it (`layering_test.go` checks this): `wire/jsonx` (the JSON conventions the wire and the data folder share: ISO 8601 dates in UTC, and an encoder with a cached plan per type that writes sorted keys and `[]`/`{}` for nil collections; decoding is `encoding/json`), `core` (model, engine, presentation: pure), `integrations/…` (`shell`, `store`, `github`, `jira`, `library`, `runner`), and `kit/…` (`coordinator`, `launch`, `demo`, `tools`). Keep them free of HTTP, WebSocket and PTY code. `server` (with `api`, `routes` and the contract harness `servertest`) puts them on HTTP and WebSocket; its handlers call one exported coordinator function and map the result. `daemon` and `cmd/beltlined` are the executable. Where a view needs logic, it goes into `core`/`kit` with tests and the API exposes it; it is never written again in a handler or in TypeScript. Files are named `<area>_<name>.go` in core (`model_`, `engine_`, `present_`) and `<package>_<name>.go` elsewhere.
- The engine (`core.EngineAdvance`) stays pure: it changes a `Run` and returns `Effect`s, and never touches GitHub, git, tmux, or the clock. The coordinator carries out effects. New flow behaviour gets an engine test first.
- The engine and the stages never ask which trigger a run came from. A stage says what it `needs` and `produces` (`Input`), a trigger kind what it `provides`, and validation checks one against the other. What a run is about is its subject's `about` (`ResourceRef`).
- Agents make every outward change (pushes, pull requests, comments, labels, reviews, ticket moves) themselves, with `gh` and `acli`; the built-in Ship, Post review and Wrap up agents do the usual ones. The app itself only reads GitHub and Jira through the `GitHub` and `Jira` interfaces, apart from the comment a policy posts when a run is held (`CommentOnHold`, off in `DefaultPolicies`; belts and runs saved before policies had their own key read it as on, `legacyPolicies`), and the backup, restore and share you start on the Library page, which write to library repositories you configured in Settings (a share can open a pull request there). A watch stage (`Watches`) waits on the run's pull request, the one under review or the newest one from the run's branch in each repository where that branch has commits to merge, and reports it merged, closed, conflicted, behind its base, with failing checks, or reviewed: approved, commented on or with changes requested (reviews hold by default, since the stages after a watch expect a merge). A watch can instead wait on the run's own issue or ticket (`WatchTarget.ticket`, `TicketWatches`) and report one of three `TicketEvent`s: a ticket under it (a sub-issue or an epic's child) added or changing status, a comment on it, or it closing. `TicketWatch` in core's `engine_ticket_watch.go` turns what it read into the event, gathering changes for a quiet period and reporting all of them together, and an agent after the watch decides what they mean; its observation stays on the run across visits. On the issue and Jira belts a fork after the watch sends a merged run to Wrap up, conflicts and a branch behind to Resolve conflicts and failing checks to Fix checks, which both go back to the watch (a `goto` to `watch` in an agent's outcomes finds the watch stage). Tests and demo mode use `FakeGitHub` and `FakeJira`.
- Every change to a run is written to disk right away through `Storage` (atomic JSON). Never keep state only in memory that a restart would need.
- Beltline runs on macOS and Linux. What differs lives in one place each: `launch.Platform` (desktop commands, the version record's `platform`), `store.SupportFolderFor` (the data folder), the service (`launch_agent.go`, `systemd_unit.go`) and the notifier (`mac_notification.go`, `linux_notification.go`); tests that assert a command line name the platform (`launch.PlatformMacOS`). The agent wrapper script is POSIX `sh`, process groups are signalled with `kill -s NAME -- -PGID`, and the Go tests run with `TZ=Europe/Amsterdam`, which the goldens assume. App data lives in `~/Library/Application Support/Beltline/` (macOS) or `~/.local/share/Beltline/` (Linux), tmux sessions on the private server `tmux -L beltline`, named `bl-…`.
- Dependencies, each with its reason. Go (`daemon/go.mod`): the standard library's `net/http` with method-and-path patterns for the server (no framework: routing, middleware and JSON need exact control over bytes); `github.com/coder/websocket` for the events and terminal WebSockets (the standard library has none; small, context-aware, no transitive dependencies); `github.com/creack/pty` for the terminal PTY and its window size; `golang.org/x/text` (collate, cases, unicode/norm) for locale-aware sorting, folding and case mapping; `golang.org/x/sys/unix` for the descriptor-relative calls (`openat` with `O_NOFOLLOW`, `fstatat`) that keep artifact reads below the data folder, and in tests for `clonefile(2)`, which clones a seeded demo folder in milliseconds; and for tests `github.com/google/go-cmp` (readable diffs). Web (`Web/package.json`, with its committed `package-lock.json`): React with React Router, TanStack Query (the cache event invalidation drives), xterm.js with its fit add-on (terminals), and for development TypeScript, Vite, Vitest with Testing Library and jsdom, and Playwright for snapshots. There is no Markdown library (the daemon sends parsed blocks) and no CSS framework. Do not add a package without a stated reason.
- Languages: the daemon is Go, chosen for a fast build and test suite. The server runs in the same process as the coordinator so every command calls it directly. The coordinator runs its work as `Turns` (`kit/coordinator/turns.go`): one turn at a time holds the lock, every external call or wait happens in a `Suspend`, background work is a counted `Spawn`, and after each turn the resource projections say which resources changed; never call `gh`, `git`, `tmux` or an agent under the lock. The web app is TypeScript and React.
- Match the design in `Web/src/theme/`: `tokens.css` (paper and slate), Archivo for display, Inter Tight for text, IBM Plex Mono for labels, and the machine drawings in `machines/`. Two appearances, Light (the default in every browser) and Dark, chosen in Settings → General and kept per browser (`state/theme.ts`, `data-theme` on the root); the OS appearance is never used. Colours are semantic tokens with a Light and a Dark value, so a new literal colour needs both. The minimum layout is 1080×680.
- Keep files roughly 200–450 lines when practical.
- The user documentation is `README.md` (install and first steps) and `docs/` (concepts, runners, configuration, security, development); `CONTRIBUTING.md` is for contributors. Update the page a behaviour change touches in the same change. `CLAUDE.md` is a symlink to this file.

## Layout

- `daemon/internal/core`, `model_*.go`: `Belt` (its trigger, repositories, base branch, `Policies`, stages and forks), `Fork` (a fork's `Route`s, and `BeltLayout`, which says where a run goes next, the path it takes and how the belt is drawn; a stage on a route names it as its `route`, a fork's stages sit together route after route, and a run keeps the route it took at each fork in `routes`; a route that `feeds` feeds into the stage after its fork: nothing on the line splits into it, only a `goto` or Send to reaches it, a `goto` into its fork never asks for it, and Feed in here (`feed(into:with:)`) puts such a fork, with the line as its empty first route, in front of a stage; `RouteEnds` says whether a route opens off the line, which a feeding one doesn't, and whether it joins the line again, which it doesn't when its last stage never moves on past the fork, and the drawings show only those connections), `ForkEditing` (the editor's changes to forks), `Trigger` (an enum: `IssueFilter`, `ReviewFilter`, `JiraQuery`, `ScheduledTask` with its `Schedule`, or manual; it saves as one object with a `kind`), `Stage`, `Input` (what stages need and produce), `Agent`, `Outcome`, `Then` (a `goto` names one stage, or one per route when it goes back into a fork, and the engine picks the one on the run's route; `route` takes a fork's route), `Run`, `Attempt`, `Subject`. A run's `Subject` is what it works on: an issue, a pull request (one run per review request, told apart by `occurrence`), a Jira ticket, or a manual or scheduled task, with its `parent` epic and open `blockers` when the trigger knows them. A `base:` label sets the run's base branch; intake leaves a subject alone while it has open blockers (`waitForBlockers`), and lists it as waiting; runs still save it under `issue`, and issue runs keep their old ids and folders. A run keeps its belt version's stages, policies and base, and copies of the agent versions its stages pin (`Run.agents`); runs and belts saved when these lived on the trigger read them from it. An agent stage pins a library agent by id and version (`AgentRef`); belts saved before the library decode `type: "build"` and the like as that built-in agent's v1. Action stages saved before agents made every outward call (`ship`, `comment`, `label`, `submitReview`, `transition`) load as agent stages (`LegacyAction`), and a run that was at one is held.
- `core`, `engine_*.go`: the state machine (`engine_engine*.go`), the `Outcome:` line parser, default outcomes, briefs and belt (`engine_defaults*.go`), the epic belt (`engine_epic_belt.go`: plan, approve, open the run's branch as the feature branch, file a wave of tickets with a `base:` label, watch the ticket, and Assess, which waits or takes the fork's Next wave route (replan, approve, file it) or its Land route (open the pull requests, merge, wrap up)), the ticket watch (`engine_ticket_watch.go`), the model pool (`engine_model_pool.go`: a stage's or agent's `alternates` are other runner, model and thinking settings its fresh sessions are spread across, to compare models; a run that comes back to the stage keeps the ones it had, any other start takes the ones fewest of the stage's slot-taking sessions use, a tie drawn at random, and `Sessions` saves the pick on the attempt before launch; adjusting a run's stage model clears them on that run), the save-time checks for belts and agents (`engine_validation*.go`), brief rendering with the outcome footer (`engine_brief*.go`), and the agent file format (`engine_agent_file.go`).
- Belt looks: `Settings.beltLook` (`BeltLook`: boxes, the default, machines or metro, set in Settings) chooses how the Overview's one Floor and every run page draw belts. The overview and run view responses carry only that look's data: `look` with `floor.boxes` or `floor.machines` and the Floor's `layout` (`FloorLayout`, computed in the daemon), and the run's `boxes` (`RunBoxes`: the box geometry `BoxLayoutMap` lays out, with each box's state and chip and each track's state, travelled, to come or a route not taken), `map` (the machines on their track, from `MapPlan` and `RouteEndGeometry`, with the filled track and the run's crate) or `metro` (`RunMetro`, from `RunMetroLayout`), all in points computed in the daemon; the run page (`RunBoxes.tsx`, `RunMap.tsx`) only places them. `StageLook` gives a box its `StageIcon` and tint (an agent's `icon`, else one its machine suggests); `OverviewBoxes` gives the boxes the Floor draws. `RunMetroLayout` draws one belt as a metro line that splits the same way at each fork. The web side draws them with `Web/src/theme/stages/` (`StageBox`, `tracks.ts`, `metroShape.tsx`, the glyphs); the belt editor keeps its own stage blocks.
- `core`, `present_insights*.go`: the Insights view (`Insights`): every belt at a glance, its first try as a 7-day rolling line with the change against the 7 days before (the line counts every run, so a short period's line has full windows, and it starts at the first day with runs), or one belt's stages with their visits, visits per run, tries per visit, first try, median time and cost per visit, each stage's models ranked. A belt can be narrowed to one version (`InsightsQuery.Version`); the stages listed, in order, are that version's, or the belt's current version's for every version, so a stage a later version removed drops out. A visit is one entry of a run into a stage on one leg, so a run sent back to a stage visits it again; attempts that were stopped count nowhere, a first try passes when its outcome's tone is good, and pause time is left out of durations. It reads only the runs, so Erase removes a run from it too; `GET /api/v1/views/insights?belt=&version=&period=` serves it.
- `core`, `present_insights_evolution*.go`: the Evolution view of one belt (`InsightsEvolution`), where a belt's Insights page opens: its finished runs in columns, one per version (small ones merged until a column has five runs, unless `separate`) or per week they finished, the columns from `from` on recent and the ones before it before (by default the last third of the runs). Six figures (lead time, time to first PR, cost, stage visits, approvals and holds, ship rate) give the recent value and its change, a statistic and the middle half per column, one dot per run, linear and log ticks and how before and recent are spread; then where the time goes (agents, waiting on you, watching the pull request, the rest), approvals, holds and AFK decisions, sends back to an earlier stage and tries again per run, cost by stage and how runs end. A run on a shadow version counts towards the live version its test shadowed. `GET /api/v1/views/insights/evolution?belt=&by=&separate=&from=` serves it; the page keeps the scale and the chosen figure in its URL.
- `core`, `present_*.go`: stage statuses (`StatusColumn`), run locations, and the metro map layout (`MetroLayout`, in points: every belt and every fork route has a row of its own, starting at its name pill; lines pull together into a snug bundle only where they travel between the same two stations or stop at the same interchange, and turn back to their rows at 45° where they part; every station has an x of its own (`present_metro_routes.go` finds each belt's paths and orders their rows; `present_metro_geometry*.go` bundles the lanes column by column, settles the rows towards where their lines meet others and sweeps the columns left to right; `present_metro_paths.go` draws the lines, stations and dots; `present_metro_text.go` puts names and run labels where they cover nothing)), shared by the views and covered by tests.
- `core/resources/agents/` (embedded): the built-in agents (Triage, Spec, Build, Verify, Ship, Wrap up, Resolve conflicts, Fix checks, Review, Post review, the epic agents Plan, Open the feature branch, File the wave, Assess, Replan and Land, and Custom), one Markdown file each: settings and outcomes in the frontmatter, the brief as the body. The app seeds nothing: a first start has no belts and no agents until you create some or install them from a library repository. Demo mode seeds the built-ins (`SeedAgents` from `DefaultsBuiltInAgents`) at their shipped version: Triage, Spec and Ship as v2, the others as v1. "Reset to default" uses them only when the library has them. A new belt starts with a trigger and no stages.
- `integrations/store`: paths and storage for belts (`belts/<id>/v<n>.json`, with `state.json` for paused and a schedule's last firing), the agent library (`agents/<id>/v<n>.md`; saved versions never change), runs (`runs/<belt>/<owner>/<repo>/<n>/run.json`, `…/pr-<n>-<request>/` for reviews, `runs/<belt>/<kind>/<key>/` for the rest, plus one folder per attempt), and settings. Your belts and agents at the root are always the live ones. `library_repos.go` holds the record of the last backup or restore (`library-repos/backup-state.json`), moves the replaced belt and agent versions into `library-backups/<time>/` and writes new ones in place. `upgrade.go` is the one-time rewrite of a data folder into the current format (`Storage.Upgrade`, run by `LaunchSessionLive` once it holds the lock and before it builds the coordinator): the settings, every belt version and state, and every run are decoded, given what core's `engine_upgrade.go` fills in (stage keys from the pinned agents, a run's source, agent copies and stage keys that keep its output files), and written back when their bytes change, each original first copied to `upgrade-backups/<time>/`. `format.json` records the format it wrote, and a folder at that format is not walked again; a folder at a newer format than this build's is refused (`NewerFormat`, a `LaunchFailureNewerFormat` launch failure) and left untouched. It is how the decoders for older files can go: once every data folder has run it, nothing on disk needs them.
- `integrations/github`: `GHCLI` over `gh`, and `FakeGitHub`. `integrations/library`: `Repos` keeps a git clone of each library repository under `library-repos/`, syncs it to its default branch, commits and pushes through `git`, and opens a share's pull request through `gh`; its tests run real `git` against local bare repositories. The library rules themselves (what an item's state is, what an install or share writes, what a backup holds) are pure functions in core: `engine_library_repo_items.go` and `engine_library_repo_plan.go`.
- `kit/coordinator`: `Coordinator` wires the parts together and is what the server talks to. `RunBook` holds the runs, applies engine events and saves every change; `Library` the belts and agents; `Intake` starts runs, running one loop over each polled `Source` (issues, review requests, Jira, in `coordinator_sources.go`), firing schedules and starting your tasks; `Sessions` starts and watches agent sessions within each stage's slots and picks each stage's checkout; `Watches` checks the pull request each watch stage waits on. `LibraryAssistant` runs the configuration assistant: one tmux conversation in the data folder that edits `belts/` and `agents/` directly. Its prompt (`AssistantPrompt`) carries the format reference built from the model's own types and defaults (`AssistantReference`), the library, what `LibraryCheck` finds wrong in it now (archived definitions aside), and the command that checks its changes (`Beltline --check-library <folder>`); the built-in agents are copied to `assistant/built-in/` for it to add. It reloads the library when their files change and lists what is wrong in the ones it changed beside the conversation. `LibraryRepos` (`coordinator_library_repos.go`) holds what each configured library repository holds and its sync state, and runs the backup, restore, install and share commands: git runs in `Suspend`, and each change reloads the `Library` and saves it at once. The Library projection covers the repositories with the belts and agents. A run copies the agent versions its stages use when it starts (`Run.agents`, `AgentSnapshot`: each agent's file), as it copies its belt version's stages, and reads them from there (`agent(_:for:)`, `agents(of:)`, `key(of:in:)`), so an install never changes it; runs saved before that read the library. A new trigger is a `Source` and a `Trigger` case.
- Shadow tests: a belt can keep one shadow version (`model_belt_shadow.go`), saved in `belts/<id>/shadow/v<n>.json` on the same version numbers, so the newest file in the belt's own folder is always live; its tests (`ShadowTest`) are in `state.json`. While a test runs, `Intake.join` starts each new run on whichever version fewer of the test's runs took (`ShadowPickArm`, a tie drawn at random) and marks it (`Run.shadow`); the run keeps that version to the end. The shadow takes live's triggers, name, base and repository bases (`ShadowDefinition`); a shadow with warnings sends every new run to live. Accept makes it live (`PromoteShadow`: it keeps its number when it is the newest, else it is saved again as the next version) and discard keeps live; both end the test, and runs on either version finish on it. Runs on a shadow leave the Overview floor (`floorRuns`) and get Work's Shadow section; the belt resource carries the running test (`ShadowSummary`), and Insights compares a test's finished runs (`present_insights_shadow.go`, `?shadow=` on the insights view). The editor opens the shadow with `?shadow=1` and keeps its unsent draft under `shadow:<id>`.
- AFK mode (`Settings.afk`, `AfkSettings`): a run's `AfkMode` (`Run.afk`, saved as `afkEnabled`) is always, never, or global, which follows the switch; it starts as its belt's `afk` (the button beside Pause belt) and you change it on the run page. While a run is in AFK mode, `Autopilot` in `kit/coordinator` gives each run that waits for you (an approval, a held agent's questions, a failed stage, any other hold) a short agent session that writes `decision.md` in the run's `afk/<n>-<stage>/` folder. `Afk` in core's `engine_afk*.go` says which stops it may take and what it may choose there, given the allowances (answer, run again, approve, carry on after holds, drop, and always leave it for you), parses the `Decision:` line and turns the choice into the same `Event` your own decision would be; `AfkBrief` renders its prompt. It never touches a run you stopped yourself, decides at most `limit` times per stage of a run, and a decision for a run that moved on is dropped. Every decision is saved in `afk/decisions.json` (`AfkDecision`), marked on the attempt it ended (`Attempt.afkDecision`), and listed on the AFK page until you mark it as checked.
- `daemon/internal/server`: the local API over the coordinator, depending on `kit` and the HTTP, WebSocket and PTY packages. `server_*.go` holds the server (start and stop; binds IPv4 `127.0.0.1` only, from `DefaultPort` 7331 up past ports in use, and reports the bound port), the middleware in order (`server_host_origin.go`: Host exactly `127.0.0.1:<port>` and any Origin exactly `http://127.0.0.1:<port>`, else 403; `server_error.go`: a domain error such as `Failure`, or any error with an `ErrorDescription`, is 422 with the message and its problems, `MissingResource` or an unknown route 404; `server_authentication.go`: `/api` needs the creator's token as a bearer or the `beltline_auth` cookie, else 401), the auth route (`/auth?token=` sets that cookie and redirects to `/`) and the static web app (`server_static_web*.go`: the app compiled into `beltlined` by the `embedweb` tag, or a `BELTLINE_WEB_DIR` directory, with an index fallback). Every handler gets a context a disconnecting client cannot cancel. `api/` has the wire types, one file per area; `routes/` the endpoint table (`routes_endpoint_registry_table.go`), the read endpoints under `GET /api/v1`, the commands under `POST /api/v1` (one per public coordinator action, plus `belts/draft/{op}`, which takes a draft and returns the edited one so the editing rules stay in the daemon), the JSON codec (`wire/jsonx` to encode, `encoding/json` to decode) and the artifact route, which serves a run's files confined to the attempt folder with `Content-Security-Policy: sandbox allow-scripts`. `events_*.go` is the `GET /api/v1/events` WebSocket: the hub compares the coordinator's resource projections after each turn, coalesces a batch of turns into one flush and sends `hello`, `changed` (a resource to refetch) and `notification`. `terminal_*.go` is `GET /api/v1/terminals?session=`: a PTY running `tmux attach-session`, read-only unless the coordinator lists the session as a Continue or assistant session; the daemon drops input on read-only ones. The contract tests (`servertest/`) start the real listener on a demo-style coordinator, call every endpoint and compare it with a golden in `daemon/testdata/golden/` (`BELTLINE_UPDATE_GOLDENS=1` rewrites them, only for an intended wire change); `Web/src/api/wire.gen.ts` is generated from the Go wire types by `TestTypeScript` (`daemon/internal/server/api/api_typescript_test.go`, which type-checks the package and the core types it reaches and fails when the file on disk differs; `BELTLINE_UPDATE_GOLDENS=1 go test ./internal/server/api -run TestTypeScript` writes it), so the web's requests and responses are typed by the daemon's own types and a wire change shows up in `npm run typecheck`. The web does not validate responses at runtime; its tests load the same goldens (`Web/src/test/golden.ts`) as fixtures. The goldens are also type-checked: `TestGoldenResponses` keeps `Web/src/api/goldenTypes.json` (each JSON golden's response type, checked against `wire.gen.ts`) and `goldenSamples.json` (Go-marshalled values of override types no golden holds, such as a deferred pause merge) current; `Web/scripts/golden-types.mjs`, run first by `npm run typecheck`, writes the gitignored `Web/src/api/golden.gen.ts`, where each golden is a literal `satisfies` its type, so a golden that drifts from the wire types fails the typecheck.
- `daemon/cmd/beltlined` and `daemon/internal/daemon`: the daemon executable. `main.go` and `command.go` handle arguments; `daemon.go` takes the data folder's lock, builds the coordinator through `LaunchSetup`, starts the server, writes `daemon.json` (mode 0600: pid, port, token, version, API version) and ticks the coordinator every two seconds (`tick_loop.go`); `daemon_open.go` signs a browser in (`beltlined open`, `--open`); `launch_agent.go` writes and loads the per-user LaunchAgent on macOS and `systemd_unit.go` the systemd user service elsewhere (`install`, `uninstall`, and `restart`; `command.go` picks by `GOOS`); `--version` prints the build and API versions; `desktop_applications.go` is Finder, VS Code, Ghostty and opening files and URLs on this Mac; `daemon_log.go` appends to `beltlined.log`, moving it to `beltlined.log.1` at start once it is past 5 MB. `make` sets the version with `-ldflags -X …/internal/daemon.buildVersion`.
- `kit/demo`: demo mode's belts (one of each trigger kind), issues, pull requests, tickets and seeded runs, and `DemoRoot`, which allocates each default demo's folder under `$TMPDIR/beltline-demo` and sweeps those of demos that are gone.
- `kit/launch`: what the daemon and tests share to start a coordinator. `LaunchSetup` builds the live and demo coordinators with the caller's notifier; `LaunchSession` takes the data folder's `OwnershipLock` (`daemon.lock`, `flock` with the owner's pid) before building one and holds it until `close()`, so a second launch on an owned folder is refused with the owner's pid; `LibraryCheckCommand` is `--check-library`, which takes no lock. `DaemonDiscovery` checks `daemon.json`, the owner's pid from the lock and an authenticated `/api/v1/version`. `DaemonInfo` (the discovery record) and `Version` live here too.
- `Web/`: the web app (Vite). `src/api/` is the client (`apiRequest<T>`, typed by `wire.gen.ts`, which also carries the enum value lists), the event connection (refetches the resource a `changed` message names, reconnects with backoff, and shows the offline banner) and one request helper per command area. `src/app/` is the shell: routes, the navigation, sign-in and offline states. `src/pages/` has a folder or file per page (Overview with its Summary and a Floor in the chosen look, drawn from the daemon's geometry, Work, Insights, Run with its stage panel and Sessions sidebar, Belts with its forms, Agents, Library, AFK, Settings). `src/components/` holds what pages share: `ActionControl` (every command control, enabled or explained from the resource's `actions`), `useCommand`'s forms, sheets, the library column, the model picker, `MarkdownBlocks` (the daemon's parsed blocks with inline emphasis, code and safe links), the `Terminal` over xterm.js and the configuration `AssistantSidebar`. `src/state/` keeps display preferences and unsent run drafts; `src/theme/` the tokens, fonts and machine drawings. `scripts/web.sh` runs `npm ci` and `vite build` and stages `Web/dist` in `daemon/internal/server/webdist/` (or `--output-dir`), which `make build` compiles into `beltlined` with `-tags embedweb`.
- `Web/snapshots/`: `make snapshots` (`scripts/snapshots.sh`) starts an isolated `beltlined --demo` and captures every case in `cases/<page>.ts` with Playwright at 1080×680, 1440×900 and 2560×1440, failing on anything drawn past a column's right edge. Install its browser once with `cd Web && npx playwright install chromium`. `BELTLINE_SNAPSHOT_ONLY` takes comma-separated case prefixes and `BELTLINE_SNAPSHOT_SIZE=WIDTHxHEIGHT` one size. A case is data: a route, sidebar state, typed steps (click, fill, select, press, wait) and API fixtures for states that would change the one shared demo daemon. `parity.ts` maps every snapshot the retired native app used to take to the case that replaces it or the reason none does. Captures are not part of `make check`; use them to check layout changes.

## Running

- Build flavours: a complete executable is `make build` (also run by `make run`, `make demo` and `make install`), which runs `scripts/web.sh` and then `go build -tags embedweb`; `go build -tags embedweb` alone fails until `make web` has staged `daemon/internal/server/webdist/`. A Go-only build (no tags: `go vet`, `go test`, `go build ./cmd/beltlined`) needs no npm and serves the API with the not-built page unless `BELTLINE_WEB_DIR` is set. `make web` updates only the staged files, so rebuild the executable to embed them. `scripts/snapshots.sh` builds a Go-only daemon and serves its own snapshot build through `BELTLINE_WEB_DIR`.
- `make run` builds `beltlined` and the web app, starts the daemon on your data folder in the foreground and opens the browser; Ctrl-C stops it. `make demo` does the same on a fresh demo folder without touching GitHub or agents. `make install` builds a release `beltlined` with the web app compiled in and registers it as your LaunchAgent; `make uninstall` removes that. `beltlined open` signs a browser in to the running daemon. `beltlined --check-library [folder]` prints what is wrong in a data folder's belts and agents and exits non-zero when anything is; it works while the folder is owned.
- `daemon.json` publishes the loopback port and a private token while the daemon runs, and `beltlined.log` keeps lifecycle and notification messages. SIGINT/SIGTERM stop the server and loop, remove discovery and release the folder; a demo folder this process created is removed. Agent tmux sessions survive a daemon restart and the coordinator picks them up again. One coordinator owns a data folder at a time: a second `beltlined` on it exits and names the owner's pid.
- `beltlined install` registers the executable it runs from as a per-user LaunchAgent that starts at login and restarts after exit, saving nonempty `BELTLINE_DATA_DIR` and `BELTLINE_TMUX_SOCKET`; keep the executable at that path while it is installed. `uninstall` removes only the registration, never data or agent tmux sessions.
- There are no releases: people install from `main` with `make install`. `scripts/notices.sh` (`make notices`) rewrites `THIRD_PARTY_NOTICES`, and CI checks it is current.
- `BELTLINE_DATA_DIR` points the daemon at another data folder; `BELTLINE_WEB_DIR` serves a built web directory (such as `Web/dist` or a snapshot build) instead of the compiled-in app, never a Vite URL, and a missing directory shows the not-built page rather than the bundle; `BELTLINE_TMUX_SOCKET` names the private tmux server (default `beltline`; the tmux tests each start their own, `beltline-test-<pid>-<n>`, and remove it); `BELTLINE_PI`, `BELTLINE_COPILOT`, `BELTLINE_CLAUDE`, `BELTLINE_CODEX` and `BELTLINE_CURSOR` point at other agent executables (Cursor's default is `cursor-agent`).
- Opt-in live tests, from `daemon/`: `BELTLINE_LIVE_REPO=owner/repo go test ./internal/integrations/github -run TestLiveGitHub` makes read-only `gh` calls, and `BELTLINE_LIVE_JQL='project = KAN' go test ./internal/integrations/jira -run TestLiveJira` read-only `acli` calls. `BELTLINE_REAL_PI=1 BELTLINE_REAL_PI_MODEL=openrouter/stealth/space-bunny-alpha go test -tags integration ./internal/kit/coordinator -run TestRealPi` runs real Pi sessions (a free model) on a tiny local repository, with the fake GitHub; `BELTLINE_REAL_CLAUDE=1` (`-run TestRealClaude`, `BELTLINE_REAL_CLAUDE_MODEL`), `BELTLINE_REAL_CODEX=1` (`-run TestRealCodex`: a triage, and an answered stage resumes its checkout's own rollout) and `BELTLINE_REAL_CURSOR=1 BELTLINE_REAL_CURSOR_MODEL=<model>` (`-run TestRealCursor`: chat allocation, one-turn completion, resume and isolation) do the same for those CLIs without external changes, and any of them (or `BELTLINE_REAL_COPILOT=1`) enables `-run TestNativePause`. Each is skipped and makes no outside calls unless its variable is set.
